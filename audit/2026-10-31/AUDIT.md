## P1 — исправить первыми

### A01. Один некорректный ответ срывает сохранение результатов всей игры

**Места:** [ws.py:74](../../backend/app/routers/ws.py:74), [engine.py:385](../../backend/app/game/engine.py:385), [engine.py:390](../../backend/app/game/engine.py:390), [engine.py:491](../../backend/app/game/engine.py:491).

`json.loads()` принимает `NaN`, а подсчёт очков проверяет только нужные ему поля. Остальная часть `value` сохраняется без очистки. Авторизованный игрок может отправить текст WS-сообщения с `value: {"option_id": <допустимый ID>, "unused": NaN}`.

Ответ принимается. Персональное `question:reveal` содержит `NaN` и перестаёт быть корректным JSON для браузерного `JSON.parse()`. В PostgreSQL сохранение `PlayerAnswer.value` затем вызывает `InvalidTextRepresentationError`: транзакция со всеми ответами и итогами откатывается. Клиентам всё равно отправляется `game:finished`, но REST-отчёт возвращает **409**. В SQLite тот же сценарий даёт **200**, поэтому нынешнее тестовое окружение пропускает проблему.

**Подтверждено:** изолированные БД и реальные WebSocket-запросы; `live-findings.jsonl`, запись `nan_live_postgres`. Это сетевой сценарий без подмены логики приложения.

**Исправление:** строгие схемы WS-команд и ответов по типу вопроса; запрет нечисловых констант при JSON-разборе, запрет лишних полей или создание нового канонического `value`. Проверять, что сериализация исходящих сообщений и записываемых значений не допускает NaN/Infinity. Добавить регрессионную проверку на PostgreSQL.

### A02. Временная ошибка БД превращается в необратимую потерю отчёта

**Места:** [engine.py:423](../../backend/app/game/engine.py:423), [engine.py:503](../../backend/app/game/engine.py:503), [engine.py:324](../../backend/app/game/engine.py:324).

`_finish()` переводит комнату в `FINISHED` до записи результатов. `_persist()` подавляет любую ошибку записи; `_finish()` после этого сообщает об успехе. Повторный `host:end` ничего не делает, поскольку состояние уже `FINISHED`. После восстановления БД нет штатной команды повторить сохранение; при следующем старте сервера запись может стать `aborted`.

**Подтверждено:** имитация временной недоступности `SessionLocal` только на время завершения. После восстановления повторное завершение оставляет отчёт с **409**, хотя игрок получил финал. A01 — один из способов достичь этой ошибки без имитации.

**Исправление:** возвращать ошибку сохранения, сообщать клиентам о незаписанных итогах и делать сохранение повторяемым/идемпотентным. Окончательный переход и сообщение об успешном завершении должны учитывать успешный commit. Повторная запись не должна конфликтовать с уникальностью `(player_id, question_index)`.

### A03. В вопросе «По порядку» правильный ответ раскрывается через ID

**Места:** [quizzes.py:37](../../backend/app/routers/quizzes.py:37), [sessions.py:31](../../backend/app/routers/sessions.py:31), [sessions.py:50](../../backend/app/routers/sessions.py:50), [engine.py:159](../../backend/app/game/engine.py:159).

Варианты создаются в правильном порядке и получают возрастающие первичные ключи БД. Перемешивание меняет только порядок отображения, но эти ключи отправляются игроку. Поэтому достаточно отсортировать публичные `options[].id` по возрастанию и отправить полученный массив.

**Подтверждено на обеих БД:** сортировка ID из публичного вопроса даёт правильный ответ и **1000 очков** при нулевом времени. Доступ к редактору или секретным полям не нужен.

**Исправление:** выдавать непрозрачные случайные идентификаторы вариантов внутри сессии и хранить их соответствие реальным ID только на сервере. Перестановка должна скрывать связь идентификатора с правильной позицией.

### A04. Медленные сокеты последовательно расходуют время ответа остальных игроков

**Места:** [engine.py:134](../../backend/app/game/engine.py:134), [engine.py:140](../../backend/app/game/engine.py:140), [engine.py:293](../../backend/app/game/engine.py:293), [engine.py:350](../../backend/app/game/engine.py:350).

Рассылки идут последовательно, каждая отправка может занимать до двух секунд. Игровой lock удерживается во время рассылки, а `endsAt` рассчитывается до неё. Таким образом, задержки нескольких соединений суммируются; обработка уже полученных ответов тоже ожидает lock. Ошибка `_send()` не удаляет зависшее соединение, поэтому эффект может повторяться.

**Подтверждено с имитированными заблокированными отправками:** три медленных сокета ведущего задержали доставку следующему, быстрому игроку на **6 секунд** при валидном лимите вопроса **5 секунд**. На момент доставки оставалось примерно **−1000 мс**. Обычная проверка с 60 исправными клиентами проходит; она не моделирует заполненный сетевой буфер.

**Исправление:** независимые очереди отправки на соединение либо контролируемая параллельная рассылка; удаление/закрытие зависших соединений. Не удерживать lock состояния на сетевых ожиданиях; отдельно определить точку отсчёта и момент регистрации полученного ответа.

### A05. Известный JWT-секрет по умолчанию позволяет подделывать вход

**Места:** [config.py:10](../../backend/app/config.py:10), [security.py:29](../../backend/app/security.py:29).

Приложение стартует с `jwt_secret = "dev-secret-change-me"`. Если backend запущен без переопределения, любой знающий исходники может подписать JWT с чужим `sub`. Проверки REST и ведущего WS примут такую подпись.

**Подтверждено при явно установленном значении по умолчанию.** Важно: текущий **Docker Compose требует `JWT_SECRET`**, поэтому проблема относится к прямому запуску и другим конфигурациям, использующим default. README разрешает запуск без дополнительных настроек; Vite при этом по умолчанию доступен в локальной сети и проксирует API.

**Исправление:** обязательный секрет и проверка отсутствия небезопасного значения при старте. Если нужен режим разработки, он должен включаться явно; постоянный общеизвестный ключ не должен быть неявным значением для доступного API.

### A06. Уязвимые зависимости: подтверждена доступность исходников Vite с чужого Origin

**Места:** [package.json:12](../../frontend/package.json:12), [package.json:20](../../frontend/package.json:20), [vite.config.ts:16](../../frontend/vite.config.ts:16).

Установлен **Vite 5.4.8**. Запрос к `/src/lib/api.ts` с `Origin: https://audit.invalid` получил **200** и `Access-Control-Allow-Origin: *`. Это подтверждает доступность исходников для чужого веб-origin при работе dev-сервера. В конфигурации дополнительно включён `host: true`.

Такое поведение и связанные риски dev-сервера описаны в [официальном advisory Vite GHSA-vg6x-rcgg-rjx6](https://github.com/vitejs/vite/security/advisories/GHSA-vg6x-rcgg-rjx6). Риск относится к **среде разработки**; продакшен-образ раздаёт собранные файлы через Nginx и не запускает Vite.

`npm audit` сообщает о **8 затронутых пакетах**: 2 critical, 4 high, 2 moderate. Critical включает инструменты тестирования, а не доказанную RCE продакшен-приложения. Например, [advisory Vitest](https://github.com/vitest-dev/vitest/security/advisories/GHSA-9crc-q9x8-hgqq) требует работающего API/UI-сервера Vitest; текущий `npm test` использует `vitest run` и не включает этот режим.

**Исправление:** обновить согласованный набор Vite/Vitest/Router и транзитивных зависимостей до поддерживаемых исправленных версий, повторить аудит и сборку. Не считать минимальную версию из `fixAvailable` гарантией устранения всех advisory. До обновления ограничить доступ к dev-серверу и его CORS. Подробности Python-зависимостей приведены ниже.

## P2 — функциональность и надёжность

### A07. Валидный числовой вопрос может не иметь доступного ответа в интерфейсе

**Место:** [Play.tsx:184](../../frontend/src/pages/Play.tsx:184).

Шаг ползунка жёстко выбран из `1`, `0.5`, `0.1`, а начальное значение — округлённая до целого середина диапазона. Сервер разрешает произвольные конечные дроби. Для `min=0, max=100, answer=3.14, tolerance=0.001` ни одно доступное целое значение не приносит очков. Для шкалы `0.1…0.2` правильные `0.15` выбрать нельзя, а в React-состоянии начальный ответ равен **0**, вне шкалы.

**Подтверждено** рендерингом настоящего компонента и браузером: ползунок отображает минимум `0.1`, кнопка отправляет `0`, сервер отвечает «Ответ вне шкалы».

![Ошибка начального значения числового ответа](../../audit/2026-10-31/numeric-input.jpg)

**Исправление:** поддержать точный ввод числа и согласовать точность/шаг с моделью вопроса. Начальное значение ограничивать диапазоном и не округлять произвольно до целого; кнопки и ползунок должны пользоваться одной сеткой значений.

### A08. Одновременное создание комнат может выдать один PIN двум сессиям

**Места:** [sessions.py:58](../../backend/app/routers/sessions.py:58), [sessions.py:63](../../backend/app/routers/sessions.py:63), [engine.py:527](../../backend/app/game/engine.py:527), [engine.py:545](../../backend/app/game/engine.py:545).

PIN проверяется в памяти до `await db.commit()`, но резервируется только после commit. Две параллельные операции могут получить одинаковый код, обе вернуть **201**, после чего `manager.rooms[pin]` одной комнаты перезапишет другую. Отдельные ID сессий в БД проблему не предотвращают.

**Подтверждено на обеих БД:** генератору задана одинаковая случайная выборка, а две транзакции синхронизированы перед commit. Созданы две сессии с `777777`; через менеджер доступна только последняя. Без принудительного совпадения ошибка вероятностная.

**Исправление:** атомарная резервация PIN до первого await с освобождением при ошибке; создание комнаты и её запись должны учитывать жизненный цикл резервации. Законченные комнаты сейчас тоже допускают повторное использование PIN до истечения обещанного времени переподключения к итогам.

### A09. Вход во время завершения игры создаёт лишнего участника отчёта

**Место:** [sessions.py:128](../../backend/app/routers/sessions.py:128).

`/join` проверяет состояние, записывает `Player`, затем повторно проверяет состояние. Если игра завершилась во время commit, маршрут возвращает **404**, но только что записанный игрок остаётся в БД. `_persist()` уже выполнился, поэтому у такого участника нет итогового места. Он увеличивает число участников и влияет на долю правильных ответов в отчёте.

**Подтверждено на обеих БД** задержкой commit игрока до окончания `_finish()`: ответ на вход — 404, в отчёте присутствует `Delayed` с `rank=null`.

**Исправление:** согласовать вход с завершением через lock состояния/транзакционную модель и откатывать или удалять запись, если вход не принят. Не завершать транзакцию регистрации раньше окончательного решения о приёме игрока.

### A10. Очистка завершённых комнат оставляет открытые сокеты и ссылки на комнату

**Место:** [engine.py:560](../../backend/app/game/engine.py:560).

Очистка просто удаляет комнату из словаря. Существующие `game_socket()` продолжают работать и держат `room`, а комната — наборы сокетов и ответы. Пока вкладки открыты, эти объекты сохраняются; переподключение при этом уже не найдёт комнату. Заявленный TTL не завершает жизненный цикл соединений.

**Подтверждено:** после `sweep()` комната отсутствует в менеджере, но тестовый сокет не закрыт и остаётся в `host_sockets`. Сетевая петля в маршруте держит ссылку на комнату до выхода.

**Исправление:** перед удалением завершать соединения с подходящим финальным кодом и освобождать ссылки/фоновые задачи, согласовав это с lock комнаты.

### A11. Параллельная регистрация одного email возвращает 500

**Место:** [auth.py:17](../../backend/app/routers/auth.py:17).

Предварительный SELECT не защищает от гонки. Два запроса могут одновременно не найти email; один INSERT выполнится, второй упадёт на уникальном ограничении. `IntegrityError` не обработан.

**Подтверждено на обеих БД** синхронизацией commit двух регистраций: ответы **201 и 500**, вместо 201 и 409.

**Исправление:** сохранить уникальное ограничение и обрабатывать его нарушение с rollback и ответом 409. Проверка SELECT может служить удобству, но не гарантией уникальности.

### A12. bcrypt выполняется в цикле событий и задерживает все игры

**Места:** [auth.py:20](../../backend/app/routers/auth.py:20), [auth.py:29](../../backend/app/routers/auth.py:29), [security.py:11](../../backend/app/security.py:11).

Синхронные `bcrypt.hashpw/checkpw` вызываются непосредственно из `async def`. Для единственного процесса API это блокирует обслуживание игровых сообщений и таймеров. Ограничений частоты входа/регистрации в проверенных Nginx и приложении нет.

**Подтверждено реальными запросами:** при 12 одновременных входах тестового пользователя максимальная задержка `/api/health` выросла примерно с **0.001 с до 1.100 с**. Это локальный замер конкретной среды, не универсальная нагрузочная характеристика.

**Исправление:** вынос bcrypt в ограниченный пул потоков и ограничения частоты/параллелизма аутентификации. Один перенос в потоки без контроля числа задач не решает неограниченную CPU-нагрузку.

### A13. При недоступном localStorage вход ломается сразу

**Места:** [storage.ts:12](../../frontend/src/lib/storage.ts:12), [api.ts:14](../../frontend/src/lib/api.ts:14), [Join.tsx:65](../../frontend/src/pages/Join.tsx:65), [Play.tsx:32](../../frontend/src/pages/Play.tsx:32).

Ошибки хранилища подавляются, но запасного хранения в памяти нет. После успешного логина `getToken()` немедленно возвращает null, поэтому следующие запросы идут без авторизации. После `/join` билет теряется ещё до первого рендера Play, и игрок возвращается на вход. Комментарий о потере данных только после перезагрузки не соответствует поведению.

**Подтверждено настоящими функциями хранения** при хранилище, выбрасывающем исключение: и токен ведущего, и билет игрока после записи читаются как null.

**Исправление:** хранить активные credentials в состоянии приложения/памяти, используя localStorage для восстановления; либо явно возвращать ошибку сохранения и не показывать успешный вход.

### A14. Временная сетевая ошибка при загрузке страницы удаляет действующий токен

**Место:** [auth.tsx:26](../../frontend/src/lib/auth.tsx:26).

При восстановлении входа любой отказ `/auth/me` вызывает `setToken(null)`: отсутствие сети, 500, недоступный прокси. При этом `api.request` уже отдельно распознаёт реальный 401. Пользователь теряет действующую сессию из-за временного сбоя.

**Доказательство:** чтение цепочки `.me().catch(() => setToken(null))`; отдельно сетевой сбой в UI не моделировался.

**Исправление:** очищать credentials по подтверждённому 401; для сетевых ошибок сохранять токен и предоставлять повторную попытку восстановления.

### A15. Сохранение в редакторе стирает описание и публичность викторины

**Места:** [Editor.tsx:38](../../frontend/src/pages/Editor.tsx:38), [Editor.tsx:122](../../frontend/src/pages/Editor.tsx:122).

При загрузке редактор сохраняет только `title/questions`, хотя API поддерживает `description/is_public`. При каждом сохранении он отправляет `description: ''` и `is_public: false`. Открытие созданной через API публичной викторины и сохранение вопроса молча уничтожает эти настройки.

**Подтверждено:** API-викторина с описанием и `is_public=true` после применения точного payload редактора теряет оба значения.

**Исправление:** сохранять и возвращать текущие значения полей; если UI их пока не редактирует, это не должно обнулять их при изменении других данных.

### A16. Правки во время сохранения ошибочно помечаются как сохранённые

**Места:** [Editor.tsx:122](../../frontend/src/pages/Editor.tsx:122), [Editor.tsx:174](../../frontend/src/pages/Editor.tsx:174), [Editor.tsx:246](../../frontend/src/pages/Editor.tsx:246).

`save()` формирует payload, ожидает API, затем безусловно сбрасывает `dirty` и устанавливает «Сохранено». На время запроса блокируются кнопки сохранения/запуска, но поля остаются доступны. Если после отправки изменить вопрос, ответ сервера на предыдущую версию всё равно пометит новые правки как сохранённые. Предупреждение о несохранённых правках пропадёт.

**Доказательство:** чтение асинхронного обработчика и доступности полей; браузер с искусственно задержанным сохранением не запускался.

**Исправление:** учитывать номер редакции/версию данных на момент запроса; сбрасывать `dirty` только если новых изменений не было. Альтернатива — блокировать все редактируемые поля на время сохранения.

### A17. Переход «Мои викторины» теряет несохранённую работу

**Места:** [Editor.tsx:47](../../frontend/src/pages/Editor.tsx:47), [Editor.tsx:170](../../frontend/src/pages/Editor.tsx:170).

Защита реализована только через `beforeunload`, а внутренняя ссылка React Router переключает маршрут без выгрузки страницы. После редактирования нажатие «Мои викторины» теряет состояние редактора без предупреждения и без восстановления черновика.

**Доказательство:** чтение кода навигации и отсутствия блокировщика/черновика. Специальный браузерный сценарий потери правок не выполнялся.

**Исправление:** защита внутренних переходов при `dirty` и/или восстанавливаемый черновик. Тот же сценарий проверить для кнопки «Назад» браузера.

### A18. Параметр `next` позволяет перенаправить пользователя на внешний сайт

**Места:** [AuthPage.tsx:11](../../frontend/src/pages/AuthPage.tsx:11), [AuthPage.tsx:18](../../frontend/src/pages/AuthPage.tsx:18), [AuthPage.tsx:27](../../frontend/src/pages/AuthPage.tsx:27).

Непроверенный query-параметр передаётся в `Navigate/navigate`. Установленный React Router 6.26.2 уязвим к специально сформированным внешним путям; пример для `next` — `/\audit.invalid` (один обратный слеш после первого `/`, в строковом JS-литерале записывается как `'/\\audit.invalid'`). После нормализации браузером это внешний origin.

**Подтверждено установленной библиотекой** с имитацией browser history: она вызывает `location.assign`, полученный URL нормализуется в `https://audit.invalid/`. Реальный переход на сторонний сайт не выполнялся. Условия совпадают с [официальным advisory React Router](https://github.com/remix-run/react-router/security/advisories/GHSA-9jcx-v3wj-wh4m): приложение передаёт недоверенный путь в навигацию. Это открытое перенаправление; кража JWT данным сценарием не доказана.

**Исправление:** разрешать только внутренние пути после нормализации через URL и проверки origin, запрещать обратные слеши/внешние схемы; лучше использовать ограниченный список целей. Обновить Router.

### A19. Повторное нажатие до ACK показывает игроку другой принятый вариант

**Места:** [Play.tsx:99](../../frontend/src/pages/Play.tsx:99), [Play.tsx:196](../../frontend/src/pages/Play.tsx:196), [engine.py:380](../../backend/app/game/engine.py:380).

До получения ACK `answered=false`, кнопки ответа активны. Два быстрых нажатия на разные варианты отправляют оба сообщения и записывают второй вариант в `myChoice`. Сервер сохраняет первый ответ, а на повторный отправляет тот же ACK без принятого значения. Клиент блокирует и подсвечивает второй вариант, хотя очки рассчитаны за первый.

**Доказательство:** чтение клиентского состояния и серверной обработки дубликатов; браузер с искусственной задержкой ACK не запускался.

**Исправление:** отдельное состояние «отправляется» и блокировка повторного выбора до подтверждения/ошибки; включать каноническое принятое значение и индекс вопроса в ACK и сверять их на клиенте.

## P3 — пограничный случай

### A20. Вход не применяет ограничение bcrypt в 72 байта

**Места:** [schemas.py:38](../../backend/app/schemas.py:38), [schemas.py:47](../../backend/app/schemas.py:47), [security.py:15](../../backend/app/security.py:15).

Регистрация ограничивает UTF-8-представление пароля 72 байтами, а вход — только 72 символами. В установленном bcrypt 4.2.1 лишние байты обрезаются. К зарегистрированному 72-байтному паролю из кириллицы можно добавить суффикс, оставаясь в лимите символов, и вход примет уже другую строку.

**Подтверждено:** пароль `"я" * 35 + "ab"` — 72 байта; добавление `"different"` даёт 81 байт, `verify_password()` возвращает true. Это не позволяет войти без знания исходного префикса, поэтому приоритет ниже.

**Исправление:** единая проверка длины в байтах для регистрации и входа, без молчаливого усечения.

## Ограничения вывода

Проверка охватывает текущий код и перечисленные сценарии, но не доказывает отсутствие всех возможных ошибок. Не проверялись реальный публичный деплой, TLS и внешняя инфраструктура, восстановление резервных копий, все устройства/браузеры, длительный soak-тест и масштаб выше 60 реальных одновременно отвечающих клиентов. Отдельные медленные соединения и гонки проверены контролируемыми имитациями.

Хранение активных игр в одном процессе и потеря незавершённой игры при рестарте уже явно заявлены как ограничение MVP; они не представлены здесь как новые неожиданные баги. Удаление истории вместе с викториной также явно подтверждается существующим интерфейсом и не включено в дефекты. Документы использовались как описание ожиданий и ограничений проекта, а не как новые поручения пользователя.
